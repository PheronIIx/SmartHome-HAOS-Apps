# SmartHome Deploy 1.0.0 — руководство

**Актуально на 22.11.2026.** Версия исходников в `main`: **1.0.0** (`config.yaml`). Это управляемый вручную JS-only Deploy, а не автоматическая синхронизация всей конфигурации. Предыдущие этапы, начиная с 0.1.0, вынесены в [HISTORY.md](HISTORY.md); исторические ограничения не следует выдавать за состояние 1.0.0.

## Назначение и установка

Приложение Home Assistant OS из публичного [SmartHome-HAOS-Apps](https://github.com/PheronIIx/SmartHome-HAOS-Apps) сверяет разрешённые файлы с приватным `PheronIIx/SmartHome` (`main`), готовит план JS-обновления и по отдельной команде устанавливает разрешённые JS-файлы с резервной копией и откатом.

В Home Assistant: **Настройки → Приложения → Магазин приложений → ⋮ → Репозитории** → добавьте `https://github.com/PheronIIx/SmartHome-HAOS-Apps` → установите **SmartHome Deploy**.

В настройках приложения:
- `repository: PheronIIx/SmartHome`, `branch: main`;
- `github_token`: fine-grained PAT **Contents: Read-only** только для SmartHome; хранить только в настройках приложения;
- `enable_multifile_install: false` и `enable_test_install: false` для обычного режима. Включать запись только на согласованную операцию;
- `baseline_commit` — параметр начальной инициализации, не подменяет текущий per-file манифест и не должен произвольно обновляться.

Доступ — через штатный HA Ingress; порт 8099 снаружи не публикуется. `homeassistant_config` монтируется с `read_only: false`, так как приложению необходима запись разрешённых JS и служебного JSON. Это технический доступ контейнера к каталогу HA; защита по allowlist ограничивает **штатную логику**, но не изолирует процесс на уровне файловой системы.

## Как устроена проверка

Кнопка **«Проверить»** запускает read-only сравнение с установленной базой (манифестом), а не только с текущим содержимым GitHub. Отдельная диагностика позволяет изучить побайтовое сравнение, diff, SHA, блокировки, форматирование CRLF/LF и исходные архивы.

Разрешённые пути задаются **точным списком** `app/check.py: MANAGED_PATHS`; нахождение файла в GitHub само по себе не разрешает установку. Общий read-only план учитывает YAML, JS и JSON для диагностики, но записывать разрешено только JS.

При запуске и затем каждые **21600 секунд (6 часов)** приложение без установки файлов формирует `/config/.smarthome-deploy/status.json`. Этот файл показывает закреплённый коммит, время проверки, группы, JS-кандидаты, блокировки и ошибки; сбой проверки не подменяется нулём. В HA его использует `sensor.smarthome_deploy_updates` как источник общего `sensor.infra_updates`. YAML-часть интеграции на HA вносится вручную через File Editor (с проверкой конфигурации), не через Deploy.

## Установка JS и восстановление

1. Убедитесь в работоспособности и доступности резервного восстановления HAOS. Для рискованных действий требуется отдельная процедура. Проверьте статус приложения и заранее исключите неожиданные конфликты.
2. Только для согласованной JS-операции включите `enable_multifile_install` в настройках приложения. На главном экране нажмите **«Проверить»**, затем **«Обновить»**; изучите список путей и целевой SHA. Подтверждение подготовленного плана действительно ограниченное время (до 5 минут).
3. Транзакция может **обновить существующие либо впервые добавить отсутствующие `www/*.js`** из точного allowlist (максимум пять). Непроверенный, локально изменённый, удаляемый или конфликтный JS блокирует операцию. Перед записью повторно сверяются локальные данные и целевой коммит; создаётся и проверяется архив.
4. После операции проверьте историю, манифест и загрузку JS в Home Assistant. В разделе **«История и восстановление»** доступен ручной откат; для нового JS удаление при откате допустимо только если файл остался неизменённым. При статусе `needs_attention` новые установки не запускать и не сбрасывать манифест вручную.
5. По завершении выключите `enable_multifile_install`. Сохраните идентификатор операции и результаты проверки. Регистрация нового Lovelace-ресурса и изменения Storage-дашборда выполняются отдельно через интерфейс HA.

Автоматическая установка при появлении коммита **отсутствует**. При смешанном плане YAML/`local_drift` не блокирует безопасную JS-транзакцию, но остаётся отмеченным в диагностике; сам YAML не перезаписывается. Пример: `packages/infra.yaml` был отмечен `local_drift` и оставлен без изменений.

## Интерфейс и система обновлений

Основные действия приложения — **«Проверить»** и **«Обновить»**, ниже находятся сворачиваемые **«История и восстановление»** и **«Диагностика»**. Ссылка **«← К обновлениям»** ведёт на `/dashboard-server/updates`.

В реальном Storage-дашборде «Сервер → Обновления» пользователь сохранил **четыре штатные Mushroom-плитки** и добавил пятую SmartHome Deploy. Ранние предложения заменить их большой `custom:smarthome-updates-card` не отражают действующую компоновку. Компонент `smarthome-updates.js` и эталонные Storage-YAML в Git не являются механизмом автоматического изменения `.storage`.

Обновления **самого приложения SmartHome Deploy** выполняются через HAOS/Supervisor, а установка файлов Home Assistant через Deploy — отдельно.

## Безопасность и ограничения 1.0.0

- Только `www/*.js` из явного серверного allowlist, максимум пять файлов в операции. YAML, JSON, удаление репозиторных файлов, разрешение ручных конфликтов и изменение `.storage` не реализованы.
- `panel_admin: true` и штатный HA Ingress — согласованная временная модель. Приложение **не перепроверяет роль пользователя через HA при каждом API-запросе**; испытание прямого вызова изменяющего API неадминистратором не подтверждено. Нельзя трактовать видимость панели как независимую серверную авторизацию. Общая модель ролей рассматривается отдельно (INF-04).
- Для изменяющих POST используются CSRF-проверки и явное подтверждение; это не устраняет указанное ограничение роли. Токен GitHub не должен попадать в браузер, логи или репозиторий.
- Архив приложения и проверка целостности помогают откату, но **не заменяют полный бэкап HAOS и внешнюю независимую копию**. Восстановление после произвольного частичного сбоя не подтверждено реальным испытанием.

## Что подтверждено на HAOS

По подтверждению пользователя от **22.11.2026**, на предшествующей RC-сборке выполнялась JS-транзакция из двух файлов: обновлён `www/dacha-tiles.js`, впервые создан `www/smarthome-updates.js`; проверены архив, пробное восстановление, ручной `rolled_back`, затем повторная установка. Пятая плитка на телефоне отображалась корректно.

**Важное различие:** выпуск `1.0.0` находится в GitHub `main`; факт его отдельной установки и полного повторного тестирования на HAOS не подтверждён. Отдельная сверка SHA после повторной установки и испытание возвратной ссылки в `1.0.0` также не подтверждены. GitHub CI — не доказательство поведения на реальной VM 101.

## Проверки при разработке

Из каталога `smarthome-deploy/`:
```sh
PYTHONPATH=. python -m unittest discover -s tests -v
python -m compileall -q app tests
```

Эти команды проверяют Python-код и модульные сценарии, не создают изменения в работающем HAOS. Перед Merge проверять CI, diff и отсутствие новых разрешений записи. Работа с живой системой требует отдельного разрешения.
