# SmartHome Deploy — версия 0.7.0 (манифест и план синхронизации)

Приложение Home Assistant OS для сравнения управляемых файлов Home Assistant с приватным GitHub и подготовки контролируемой синхронизации. В 0.7.0 манифест и многофайловый план работают только на чтение; полноценная многофайловая запись ещё не реализована.

## Установка с телефона

1. В Home Assistant откройте **Настройки → Приложения → Магазин приложений** (в некоторых версиях: **Настройки → Дополнения → Магазин дополнений**).
2. В меню **⋮ → Репозитории** добавьте **https://github.com/PheronIIx/SmartHome-HAOS-Apps**.
3. Обновите магазин и найдите **SmartHome Deploy (read-only preview)**.
4. До установки создайте резервную копию HAOS через штатный интерфейс и убедитесь, что есть доступ к Proxmox для восстановления.
5. Установите приложение, но перед первым запуском настройте его:
   - `repository`: `PheronIIx/SmartHome`;
   - `branch`: `main`;
   - `github_token`: fine-grained GitHub PAT с доступом **только к PheronIIx/SmartHome**, разрешение **Contents: Read-only**. Токен вводится только в настройках приложения.
6. Запустите приложение и откройте его веб-интерфейс через **Открыть веб-интерфейс**. Нажмите **Проверить**.
7. Сверьте результаты с текущими файлами; при ошибке используйте **Журнал** приложения, но не передавайте токен в переписку.

## Безопасность

- Доступ к домашней конфигурации в контейнере: `homeassistant_config` с `read_only: true`.
- Отсутствуют операции записи и API установки; сервер отвечает только на GET, POST отклоняется.
- Приложение не запускает службы HA, Proxmox, Frigate и не изменяет дашборды.
- Веб-интерфейс через Ingress, без публикации пользовательского сетевого порта.
- `panel_admin: true` скрывает боковую панель от неадминистраторов, но **сам по себе не является полноценной серверной авторизацией**; до разработки действий установки понадобится отдельная схема проверки прав.
- Версия 0.1.0 проверена на реальной HAOS: сборка, Ingress, подключение к приватному GitHub и сравнение выполнялись. **Новые функции 0.2.1 ещё не проверены на HAOS.**

## Что сравнивается

Ветка `main` приватного репозитория содержит источники в `home-assistant/`. Из неё учитываются:
- `configuration.yaml`, `automations.yaml`, `scripts.yaml`, `scenes.yaml`;
- `packages/*.yaml`;
- `www/*.js`;
- `www/plans/*.json`.

Версия **0.2.1**: для статусов «Изменён» и «Отсутствует» появляется кнопка **«Различия»**. По нажатию приложение отдельно получает из GitHub файл строго из коммита, показанного вверху, и строит unified diff: строки с `-` — текущий Home Assistant, строки с `+` — GitHub. Различия только в CRLF/LF и финальных переводах строк отмечаются отдельно. Максимум 256 КиБ на каждый файл и 2500 строк diff; большие файлы не раскрываются целиком. Данные для сравнения доступны в браузере только через Ingress. Содержимое разрешённых файлов может включать чувствительную локальную информацию: не публикуйте скриншоты diff с адресами/ключами без проверки. Изменения устанавливать по-прежнему нельзя.

Приложение показывает статусы `same`, `modified`, `missing`, `error` для файлов, имеющихся в GitHub. Сравнение основано на Git blob SHA-1 точного зафиксированного коммита; это побайтовое сравнение, а не YAML-валидация.

Исключены `secrets.yaml`, `.storage`, `ssh/`, `docs/`, `frigate/` и `dashboards/server.yaml`. Этот MVP не исследует лишние файлы на HA.

## Разработка и проверки

`PYTHONPATH=. python -m unittest discover -s tests -v` — тесты сравнения, в том числе проверка путей и отсутствующего токена.

Этот отдельный публичный репозиторий **не содержит** домашние конфигурации, токены или ключи. Изменения в нём публикуются независимо от приватного `PheronIIx/SmartHome`.

Код проекта: [публичный репозиторий](https://github.com/PheronIIx/SmartHome-HAOS-Apps). Архитектура и будущий механизм развёртывания хранятся в приватном SmartHome.

## Формат строк и классификация в 0.2.1

При общей проверке для файлов, отличающихся по байтам, приложение дополнительно сравнивает текст с нормализацией CRLF/LF и завершающих переводов строки. Статус `format_only` означает, что содержимое идентично после такой нормализации. Статус `modified` означает реальное отличие содержимого. Статус `unclassified` означает, что дополнительная диагностика не выполнена (например, лимит 256 КиБ или ошибка GitHub); это не доказательство изменения содержимого. Текущий файл на HA не изменяется.

Для `format_only` на кнопке «Различия» показывается только пояснение с CRLF и завершающими переносами, без огромного diff. Для `modified` diff игнорирует CRLF/LF, но не игнорирует изменения пробелов или содержимого.

## 0.3.0 — подготовка установки без записи

Добавлена кнопка **«Подготовить план»**. Укажите `baseline_commit` — SHA подтверждённой исходной версии файлов. Для первого испытания по совместно проверенным 15 файлам используется `8de108c40d4ffd0f10039fe4e7e9eec047494974`. Это **базовый ориентир для сравнения**, а не отметка о реальной установке: идентичность была подтверждена по содержимому с допуском CRLF/LF.

Приложение сравнивает список разрешённых файлов в базовом коммите с целевым коммитом ветки `main`, проверяя локальные файлы относительно базовой версии. Возможные исходы:
- `no_change` — в GitHub файл не менялся относительно базы, локальная версия ей соответствует;
- `candidate_review` — GitHub отличается от базы, локальный файл базе соответствует; требуется ручной просмотр и подтверждение;
- `blocked_local_drift` — локальное содержимое отличается от базы, отсутствует либо не удалось надёжно сверить; **запрещать будущую установку до разбора**;
- `new_file_review`, `deletion_review` — новые или удалённые в GitHub файлы требуют отдельного согласования.

Сверка только для файлов размером до 256 КиБ; превышение лимита блокирует уверенное заключение. Никакого деплоя, бэкапа или отката в версии 0.3.0 ещё нет. Информация о планируемых изменениях **не является** автоматическим разрешением на установку. Не менять baseline_commit автоматически после PR: для последующих установок потребуется модель проверенной установленной версии и журнал.

## 0.3.1 — исправление просмотра текстовых различий

Исправлена нормализация настоящих CRLF и LF перед `unified_diff`. Раньше при **реальном** изменении (например, добавлен один комментарий в `www/house-card.js`) в окне различий отображался почти весь файл, потому что код искал буквальные символы `\\r\\n`, а не окончания строк. Теперь показывается только реальное изменение и несколько строк контекста. Статусы и алгоритм построения предварительного плана из 0.3.0 не менялись. Приложение остаётся строго **только для чтения**.

## 0.4.0 — библиотека резервирования и тестовый откат

Внутри приложения добавлен модуль `app/backup.py`, пока **без кнопок и HTTP API**. Это подготовительный этап, функции вызываются только из автоматических тестов:

- `create_snapshot(paths, source_commit)` — атомарно сохраняет разрешённые файлы в `/data/backups` (не в `/config`) вместе с SHA-256 и исходным Git SHA.
- `verify_snapshot(name)` — проверяет целостность архива и каждый путь против whitelist.
- `rehearse_restore(name, target_directory)` — восстанавливает копию **только в изолированный каталог** `/data/restore-rehearsals/<имя>` и сверяет содержимое. Файлы HA не затрагивает.
- Запрещены символьные ссылки, сторонние пути, дубли, файлы более 256 КиБ; применяется общий лимит 16 МиБ.
- Резервные копии лежат в каталоге данных приложения, предназначенном для хранения состояния между обычными перезапусками приложения. Это не внешняя аварийная копия. Сохранность при переустановке и реальное восстановление на HAOS ещё предстоит проверить отдельно.

**Важное ограничение:** кнопки создания копии в веб-интерфейсе версии 0.4.0 ещё нет, как и записи в конфигурацию HA. Прежде чем включать любой мутирующий HTTP endpoint, необходимо спроектировать административную авторизацию, CSRF-защиту, подтверждение и журнал операций. Самостоятельно выполнять тестовый откат в `/config` нельзя.

## 0.5.0 — резервные копии через Ingress (без записи в HA)

- Добавлены кнопки **«Создать резервную копию»**, **«Проверить»** и **«Проверить восстановление»**, а также список архивов с датами и размерами.
- Создание архива включает **все существующие управляемые файлы из актуального дерева GitHub**, которые доступны для сравнения на HA. Если хотя бы один отсутствует или не может быть проверен, операция блокируется. Файлы с локальными изменениями **архивируются как есть**, без замены.
- Архив создаётся в `/data/backups` с SHA-256 и проверяется сразу после создания. Проверка существующего архива повторно вычисляет SHA-256.
- Тестовое восстановление допускается **только в `/data/restore-rehearsals/test-...`**. Запись в `/homeassistant` и установка из GitHub по-прежнему запрещены.
- Для POST применяется ingress-only ограничение по IP прокси, панель `panel_admin: true`, проверка `Sec-Fetch-Site`, `Origin` (когда передан) и секретный заголовок CSRF, выдаваемый только через Ingress. Приложение не открывает внешний порт. **Полномочия пользователя обеспечивает HA Ingress**; само приложение не получает токен пользователя и не может отдельно подтвердить его роль. Эту границу доверия нужно проверить на HAOS до добавления установки.
- Список архивов — это метаданные файлов на диске, а не гарантия целостности. Проверять нужно отдельной кнопкой.
- Архивы в `/data` должны переживать штатный перезапуск приложения, но это **не проверено на реальном HAOS**. Не считать их независимой внешней резервной копией.
- Не реализованы автоматическое резервирование перед установкой, запись в HA, реальный откат, политика ротации и проверка полных копий Supervisor/Proxmox. Эти этапы будут согласовываться и тестироваться отдельно.

### Проверка на HAOS

1. Установить 0.5.0 после зелёных тестов и merge.
2. Открыть Ingress SmartHome Deploy от имени администратора и нажать «Создать резервную копию».
3. Убедиться, что создан архив со всеми ожидаемыми файлами, проверить его SHA-256 кнопкой «Проверить».
4. Нажать «Проверить восстановление» и убедиться в сообщении об успешном тесте. Рабочая конфигурация HA не должна измениться.
5. Перезапустить приложение и убедиться, что архив виден и снова проходит проверку.

## 0.6.0 — тестовая установка и откат одного JS-файла

**Статус 0.6.0: объединено и проверено на HAOS.** Проверены создание/проверка резервной копии, тестовое восстановление, установка разрешённого комментария в `www/house-card.js`, проверка архива и ручной откат. Эти проверки не подтверждают многофайловый деплой.

- Единственный разрешённый путь: `www/house-card.js`; разрешено только добавление заранее утверждённого тестового комментария. YAML/JSON, автоматизации, NUT, охрана и Frigate не устанавливаются.
- **ВАЖНО:** монтирование `homeassistant_config` меняется с `read_only: true` на `read_only: false`. Процесс контейнера технически получает доступ на запись ко всему каталогу HA. Программный whitelist ограничивает штатные операции, но не заменяет изоляцию ОС.
- По умолчанию `enable_test_install: false`; для теста включить опцию в настройках приложения и перезапустить его.
- Предпросмотр формирует одноразовый план на 5 минут с SHA-256 локального файла и целевого GitHub blob. Изменение относительно утверждённой базы допускает только согласованный комментарий.
- Перед установкой: повторная проверка байтов, создание **автоматического** архива одного файла, проверка SHA-256, запись журнала в `/data/deploy-history`. Затем временный файл, `fsync`, атомарная замена и проверка результата.
- Откат требует отдельного подтверждения, совпадения текущих байтов с установленной версией, проверки исходного архива и новой копии перед возвратом. Незавершённые транзакции блокируют дальнейшие записи.
- История и архивы сохраняются в `/data`, автоматической ротации нет. Независимый путь восстановления HAOS/Proxmox обязателен для аварий.
- Ingress и CSRF остаются обязательными. **Роль администратора отдельно внутри приложения не проверяется:** `panel_admin` и Ingress — граница доверия, которую нужно оценить до производственного развёртывания.
- Внешние процессы могут параллельно менять файлы; проверки предотвращают обнаруживаемые конфликты, но не обеспечивают межпроцессную транзакцию с Home Assistant.

### Безопасный порядок испытания

1. Дождаться CI и ревью PR, **не обновлять приложение сразу после merge**.
2. Проверить полный бэкап HAOS и независимый способ восстановления до первого теста writable mount.
3. Обновить приложение с выключенным `enable_test_install`, проверить старые функции.
4. Включить опцию, перезапустить приложение, подготовить тестовый план, сверить путь и SHA.
5. Подтвердить установку, проверить статус `installed`, архив и работу карточки.
6. Подтвердить откат, проверить возврат исходных байтов и наличие архива отката.
7. Выключить `enable_test_install` и перезапустить приложение. Учесть: сам writable mount останется до отдельного изменения манифеста.

Установка и откат одного тестового изменения в `www/house-card.js` **проверены на HAOS**. Writable mount остаётся существенным риском: процесс приложения технически имеет доступ на запись ко всему каталогу HA, хотя код 0.6.0 жёстко ограничивает штатную запись одним файлом.

## 0.7.0 — per-file manifest и read-only план синхронизации

**Статус: реализация в PR; до merge и отдельной проверки на HAOS не обновлять приложение.**

### Allowlist

Вместо широких масок применяется точный серверный allowlist: корневые YAML-файлы; пять существующих пакетов; пять JS-ресурсов и `www/plans/g45.json`. Новые файлы автоматически не включаются. Исключены Storage-дашборды Home Assistant (включая `dashboards/server.yaml`), `secrets.yaml`, `.storage`, `ssh/`, `docs/`, `frigate/` и исходники приложения.

### Манифест установленной версии

- Однократная операция создаёт `/data/installed-manifest.json`; в каталог Home Assistant она не пишет.
- Исходные версии путей берутся из `baseline_commit`.
- Новые allowlist-пути принимаются в манифест только если локальный файл совпадает с текущей версией GitHub (с допуском нормализации CRLF/LF). Локальные расхождения остаются вне манифеста.
- Для каждого пути сохраняются source commit, Git blob SHA, SHA-256 и размер. Манифест создаётся атомарно, с fsync и правами 0600; повторная инициализация запрещена.

### План синхронизации

- «Проверить обновления» сравнивает локальные файлы с per-file baseline, а не с текущим GitHub.
- Для конфликтов доступны diff HA ↔ установленная база и HA ↔ GitHub.
- План строго read-only. Многофайловая установка, расписание, интеграция мастер-кнопки в дашборд «Сервер», обновление baseline после установки и транзакционный откат остаются следующими этапами DEV-06.

### Проверки и границы

Автоматические тесты покрывают точный allowlist, одноразовую инициализацию, безопасное принятие нового пути, локальное расхождение, per-file классификацию и оба diff. CI выполняет compileall, unit tests, проверку версии манифеста приложения и синтаксиса JS.

Версия 0.7.1 установлена пользователем на HAOS. Пользователь подтвердил создание и проверку архива из 15 файлов, а также тестовое восстановление 15 файлов без изменения конфигурации HA. Многофайловая установка не проверялась и остаётся отключённой. Существующий тестовый endpoint 0.6.0 остаётся единственным механизмом записи в HA.

## 0.7.1 — исправление allowlist и резервирования

- Удалён `dashboards/server.yaml` из allowlist: дашборд «Сервер» создан через Storage-редактор Home Assistant и не является файлом `/config/dashboards/server.yaml`. Приложение не читает и не изменяет `.storage`.
- Старые манифесты 0.7.0 могут содержать этот путь. При чтении он отбрасывается из активного набора в памяти; файл манифеста и данные HA автоматически не переписываются.
- Резервирование использует установленный per-file manifest: отсутствующий в HA новый файл GitHub, которого нет в manifest, пропускается и перечисляется в результате; отсутствие ранее установленного файла блокирует архив.
- Без manifest отсутствие файла остаётся блокирующим, поскольку нельзя достоверно отличить новый путь от удалённого пользователем ранее установленного файла.
- Файлы из manifest, которые позднее исчезли из GitHub, но остались локально, также включаются в архив. Локальные изменения архивируются в текущем виде.
- Неопределённые статусы, ошибки доступа, символьные ссылки и повреждённые манифесты продолжают блокировать резервирование. Проверка целостности ZIP и тестовое восстановление не меняются.
- Успешный результат явно перечисляет новые неустановленные файлы, пропущенные из архива.

Исправление не устанавливает файлы в Home Assistant и не включает многофайловую запись.

## 0.7.2 — форматирование не считается обновлением

- Планировщик сравнивает содержимое установленного GitHub blob с целевым blob `main` после нормализации только CRLF/LF и завершающих переводов строки.
- Если содержимое идентично после такой нормализации, путь получает отдельное действие `format_only`: не включается в счётчик обновлений и не предлагает Diff/перезапись.
- Локальное расхождение относительно установленной базы по-прежнему проверяется отдельно. Реальное локальное изменение содержимого остаётся конфликтом; только окончания строк не блокируют настоящее обновление.
- Если blob установленной или целевой версии невозможно проверить, действие `blocked_unverified` блокирует путь и отражается в счётчике конфликтов.
- Реальные изменения содержимого продолжают получать `candidate_review`. Многофайловая установка остаётся отключённой.

**Статус: план, испытание на HAOS не проводилось.** Не выполнять установку, merge или изменение работающих файлов без отдельного согласованного запуска.

**Предварительная зависимость:** дашборд «Сервер» хранится в Storage — его конфигурация не развертывается через Deploy. В PR #16 уже реализована возможность добавления нового JS при отсутствующем пути, но **новый путь должен быть отдельно согласован и включён в точный серверный allowlist**. **Ограничения перед тестом:**
1. Ревью PR #16, успешный CI, отдельно проверенный на HAOS административный доступ через Ingress; доступ неадминистратора к mutating API должен быть исключён или установка остановлена.
2. Свежая штатная полная резервная копия HAOS и независимый путь восстановления через Proxmox; техническая проверка доступности этих резервных копий.
3. `enable_multifile_install: false` до начала согласованной записи, `enable_test_install: false`; не изменять YAML, Storage, другие JS или allowlist в ходе самого испытания.
4. Подтверждено отсутствие незавершённых операций, корректный манифест, неизменённый GitHub target commit, разрешённый JS-only план (максимум 5 файлов); нет локальных конфликтов, непредусмотренных добавлений или удалений.
5. Не использовать искусственные правки рабочих JS-карточек; тестовое изменение только в согласованном компоненте панели «Обновления».

**Последовательность:**
1. Установить/обновить приложение 0.10.0 *только после отдельного разрешения пользователя*, оставить запись выключенной. Проверить отображение интерфейса, read-only план, историю и загрузку диагностики на ПК и телефоне.
2. Проверить, что неадминистратор не может вызывать установку через Ingress; при неудаче остановить испытание.
3. Согласовать имя JS-компонента и добавить его путь в точный allowlist новой версии Deploy; проверить, что файла нет в HA и манифесте. Не регистрировать несуществующий ресурс Lovelace заранее.
4. Создать первую полезную версию JS-компонента в репозитории SmartHome, пройти ревью и объединить в `main`. Зафиксировать commit; убедиться, что план содержит ровно ожидаемое добавление, без неожиданных обновлений других путей.
5. Включить тестовый режим, нажать «Проверить», затем «Обновить», сверить пути и SHA. Подтвердить установку явно в пределах 5 минут с момента подготовки плана. Не запускать повторно, если состояние неясно.
6. Проверить журнал, целостность архива, появление JS и новую запись манифеста; убедиться, что остальная HA-конфигурация не изменилась. Отдельно зарегистрировать Lovelace-ресурс и добавить карточку в Storage-дашборд после проверки возможности загрузки нового JS.
7. Перед откатом отключить новый Lovelace-ресурс/карточку в Storage, чтобы не оставлять битую ссылку. Проверить контролируемый ручной откат: новый JS исчезает, старый манифест восстановлен; затем обновление заново только после оценки результатов.
8. Выключить `enable_multifile_install` после теста; зафиксировать commit, идентификатор операции, результаты и ограничения.

**Условия остановки:** любое сомнение в правах доступа, неверный набор файлов, локальный конфликт, несовпадение SHA/бэкапа/манифеста, ошибка записи или отката, `needs_attention`, незавершённая операция, отсутствие доступа к независимой резервной копии. **Критерий успешности:** получена проверяемая первая установка нового JS-компонента панели, архив подтверждён, журнал и манифест корректны, ручной откат безопасно удаляет добавленный файл; никакие другие управляемые файлы не затронуты. Разработка Lovelace-интерфейса для управления Deploy остаётся отдельной задачей.

### Согласованная модель доступа Deploy · 20.11.2026

**Решение пользователя:** на текущем этапе SmartHome Deploy использует штатное ограничение панели Home Assistant — `panel_admin: true` при `ingress: true`. Дополнительную настройку `authorized_admin_user_ids`, ручной список ID и связанную с ним проверку в приложении **удалить**. Нельзя утверждать, что любой прямой запрос от авторизованного неадминистратора гарантированно отклоняется самим приложением. До фактической проверки поведения Supervisor Ingress на HAOS это риск, принятый в рамках временного решения. Режим установки выключен по умолчанию; до испытаний не включать его. Если тесты покажут доступ к изменяющим API для неадминистратора, остановить испытания и вернуться к пользователю для отдельного архитектурного решения.

Для записи JS требуется отдельная согласованная процедура, полный бэкап, проверенный план и контролируемый откат.

**Будущая ролевая модель:** единая система ролей и управление разрешениями для нескольких домов (INF-04) обсуждаются и проектируются отдельно. До её согласования не создавать новую архитектуру полномочий или настройки авторизации для Deploy.

## DEV-07 — статус обновлений для общей панели (1.0.0-rc.3; до проверки на HAOS)

**Согласованная граница:** SmartHome Deploy остаётся JS-only, запись YAML, Storage и обновление самого add-on не добавляются. `boot: auto` позволяет проводить фоновую **read-only** проверку при запуске приложения и затем каждые 21600 секунд (6 часов). Ни планировщик, ни чтение JSON не вызывают install/rollback.

**Публикация:** модуль `app/status_export.py` использует уже существующий `sync_plan.prepare_sync_plan()` и его per-file baseline. Результат атомарно сохраняется в отображаемую папку HA как `/config/.smarthome-deploy/status.json` (путь внутри add-on: `/homeassistant/.smarthome-deploy/status.json`). Файл с mode 0644 доступен локальному command_line-сенсору HA; токен GitHub не записывается в JSON.

Формат `schema_version: 1`:
- `status`: `ok`, `blocked`, `unconfigured` или `error`;
- `checked_at`: время **успешной** проверки UTC; при ошибке `null`, а `attempted_at` фиксирует неудачную попытку;
- `target_commit`: полный закреплённый SHA GitHub main либо `null`;
- `available_count`: количество JS update/add, потенциально допустимых текущей JS-only моделью; `blocked_count`: конфликтные, удаляемые и неустанавливаемые YAML/JSON кандидаты;
- `groups`: группы компонентов по точному пути из allowlist; `files`: объекты `{path, group, action, status}`; `message`: описание ограничения.

`available_count` не означает разрешение на установку: реальная операция всё равно проходит проверки полномочий Ingress, настройки `enable_multifile_install`, SHA, свежести плана, бэкапа, состояния файлов и ограничения JS-only. Группа `cards` охватывает только `www/*.js`; `plans` — `www/plans/`; `packages` — YAML-пакеты; `configuration` — остальные управляемые файлы. Все не-JS-кандидаты помечаются `blocked`, независимо от наличия изменения в репозитории.

**Ошибки и целостность:** публикация выполняется через временный файл внутри каталога, `fsync` и `os.replace`. Символические ссылки для корня и статусного каталога не проходятся. При ошибке планировщика публикуется `status=error` и `available_count=null`, а не ложный ноль. Если запись невозможна, старый файл остаётся; Home Assistant считает результат устаревшим через 12 часов и показывает неполные данные. При отсутствии файла сенсор недоступен. Публикация не относится к управляемому allowlist и не меняет baseline.

**Интеграция HA:** приёмник `sensor.smarthome_deploy_updates` и расширенный `sensor.infra_updates` находятся в `SmartHome/home-assistant/packages/infra.yaml` и должны быть внесены **вручную** через File Editor с последующей проверкой конфигурации HA. Обе Storage-панели подключают `custom:smarthome-updates-card` через UI Home Assistant. Их исходники в Git — лишь эталонные копии. Текущие PR SmartHome #10 и SmartHome-HAOS-Apps #17 переработаны вместе: это не два независимых счётчика.

**Порядок испытания, без автоматического деплоя:** после ревью и Merge PR обновить приложение по штатной процедуре add-on; убедиться, что `enable_multifile_install=false`; проверить запуск read-only опроса и `status.json`. Затем отдельно согласовать ручное внесение YAML, пройти HA Check configuration и проверить `sensor.smarthome_deploy_updates` / `sensor.infra_updates`. Вручную зарегистрировать JS-ресурс и настроить обе панели. Для первой реальной JS-установки/отката нужен отдельный согласованный тест с полным бэкапом HAOS. До него статус: **не проверено на HAOS, не готово к безусловному Merge**.


## 1.0.0-rc.4 — JS-транзакция независимо от YAML (21.11.2026)

Подготовка `multifile.prepare()` выбирает из общего read-only плана только изменённые пути, разрешённые строгим JS allowlist (`www/*.js`). Не-JS изменения (включая `packages/infra.yaml` с локальным отличием от старого baseline) остаются в общем плане, `status.json` и диагностике со своими блокировками, но не мешают подготовке безопасного JS-набора. Манифест и содержимое не-JS файлов не изменяются при установке и откате JS. Наличие только YAML-изменений не позволяет создать пустую транзакцию.

Любое конфликтное/непроверенное/удаляемое изменение **разрешённого JS** по-прежнему блокирует всю JS-транзакцию. Проверки SHA, pinned commit, локального состояния, snapshot/verify, атомарной записи, журнала, ручного подтверждения и отката сохранены. Опция `enable_multifile_install=false` остаётся по умолчанию; новая версия не означает разрешения на установку или деплой. Регрессионные тесты покрывают смешанный план с YAML drift, запрет JS-конфликтов и сохранение YAML в манифесте после install/rollback.


## 1.0.0-rc.5 — возврат на панель «Обновления» (22.11.2026)

В верхней строке веб-интерфейса SmartHome Deploy добавлена ссылка **«← К обновлениям»**. Она ведёт на `/dashboard-server/updates` в верхнем окне Home Assistant (`target="_top"`), включая открытие приложения через Ingress-панель `/app/78ff2ce6_smarthome_deploy`. Кнопка не выполняет установку, не меняет права и не вызывает API; работает как обычная навигационная ссылка. На телефоне строка переносится по ширине экрана.

**Ввод:** после Merge обновить SmartHome Deploy до `1.0.0-rc.5` через интерфейс приложений Home Assistant, затем открыть его с пятой плитки «Сервер → Обновления», нажать «← К обновлениям» и проверить возвращение на пять плиток. Повторить на телефоне. Если ссылка не видна, обновить страницу приложения. Это обновление приложения, не JS-синхронизация файлов Home Assistant через Deploy.

**Результат испытаний на 22.11.2026:** пользователь подтвердил успешную JS-установку и корректное отображение пятой плитки на телефоне. Откат JS на реальном HAOS пока **не проверен**. Для испытания отката: до операции проверить свежий полный бэкап HAOS, зафиксировать текущие SHA/состояние файла, использовать только разрешённый JS-путь из allowlist, установить контролируемое изменение через штатную JS-транзакцию и выполнить ручной откат из истории. Сверить SHA до/после и журнал. Не трогать `packages/infra.yaml`, манифест вручную или `.storage`. Выполнять установку и откат только после отдельного подтверждения конкретного тестового изменения.

**Уточнение к историческим разделам выше:** прежние инструкции о замене четырёх плиток одной большой карточкой устарели. На «Сервер → Обновления» используются четыре исходные Mushroom-плитки плюс пятая SmartHome Deploy. `custom:smarthome-updates-card` там не требуется. Эталонный Storage YAML хранится в SmartHome, изменения в живой дашборд вносятся через UI Home Assistant.
